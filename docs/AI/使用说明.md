# 自主学习游戏 AI：代码与运行

当前状态：首版训练流程已跑通。11 项 Python 测试、9 项 Unity 测试、真实物理对局、CPU 短训练、搜索续训和跨进程回放已通过。现有检查点用于流程验证，尚未训练出经过充分评估的强 AI。具体结果见 [首版验证报告](首版验证报告.md)。

## 1. 准备 Python 环境

首次克隆后先补齐 Git LFS 资源。xLua 动态库、盘面模型等只有指针时，项目能编译 C#，但无法正常运行：

```powershell
$LfsCache = Join-Path (Get-Location) '.utmp/game-ai/lfs'
git -c "lfs.storage=$LfsCache" lfs pull
```

在项目根目录运行：

```powershell
.\Tools\GameAI\setup.ps1
```

脚本在 `.utmp/game-ai/venv` 建立独立环境。当前依赖固定为 PyTorch 2.6.0 和 NumPy 2.0.2，以兼容本机 Python 3.9；CPU 版本可用于开发和小规模训练。使用更新 Python 时应先确认这些固定版本有对应 wheel。

训练命令默认 `--device cpu`。CUDA 需要另外安装与显卡、驱动兼容的 PyTorch GPU 版本，再使用 `--device cuda`。当前机器安装的是 CPU 版；仅改变参数不会使 CPU 版获得 CUDA 支持。

## 2. 构建真实游戏环境

使用项目指定的 Unity 2022.3 打开项目，待脚本与资源导入完成，执行菜单：

```text
Marbles ECS > AI > Build Training Player
```

或用项目脚本传入实际编辑器路径：

```powershell
.\Tools\GameAI\build.ps1 -UnityEditor '实际的 Unity.exe 完整路径'
```

构建采用 Build Settings 中第一个启用且存在的场景；当前为 `Assets/Scenes/TestScene.unity`。输出为 `.utmp/game-ai/player/GameAI.exe`，旁边的 `manifest.json` 记录源码、场景和资源哈希。构建日志位于 `.utmp/game-ai/build.log`。批处理脚本传入 `--game-ai-build`，阻止首次导入时由 Excel 自动覆盖当前 `GameBalance.json`。

场景需包含 Campaign Controller、开启自动移动的发射器，以及已绑定盘面和放置平面的 `DevicePlacementUI`。版本 1 明确拒绝手动发射器模式。它保留原场景操作范围，采用有限位置、45 度旋转增量和三个投入档位。

普通启动游戏不启用 AI。只有传入 `--game-ai-port` 才创建本机服务并切换到明确步进。服务仅绑定 `127.0.0.1`；Python 启动和关闭自己的 Player 进程。

无界面 Player 使用 MRes 的无渲染资源加载选项，保留网格、Renderer 组件、碰撞、物理材质与 Lua，跳过 GPU 材质和纹理。图形模式仍使用原渲染资源加载路径。

## 3. 先做流程与回放检查

```powershell
.utmp\game-ai\venv\Scripts\python.exe Tools/GameAI/run.py evaluate --random --episodes 2 --max-actions 128 --output .utmp/game-ai/runs/smoke
.utmp\game-ai\venv\Scripts\python.exe Tools/GameAI/run.py verify-replay --trace .utmp/game-ai/runs/smoke/episode-00001.json
```

128 次动作是短流程检查预算，达到上限会标为 `truncated`，不代表正常失败或通关。完整评估使用更高预算，观察正常终局比例。回放会逐操作检查摘要、奖励和最终状态；不一致就报错，不继续报告可信搜索结果。

## 4. 训练和搜索

先训练不带搜索的网络，以检查模型、奖励和采样链路：

```powershell
.utmp\game-ai\venv\Scripts\python.exe Tools/GameAI/run.py train --episodes 100 --device cpu --output .utmp/game-ai/runs/warmup
```

之后用检查点启动商店/布局搜索与策略蒸馏：

```powershell
.utmp\game-ai\venv\Scripts\python.exe Tools/GameAI/run.py train --checkpoint .utmp/game-ai/runs/warmup/latest.pt --episodes 100 --search 16 --rollout-steps 64 --output .utmp/game-ai/runs/search
```

这里的 100 局、16 次搜索和 64 步试演是命令示例，不能据此保证学会游戏或达到某个分数。应先根据每局成本和真实评估曲线调整。

每个搜索模拟都会在第二个独立 Player 中重放到根节点，检查观察一致性，再随机化之后的未来。实际 Player 不提供随机化命令权限。真实对局种子由实验调度器管理，不输入神经网络。

模型采用集合注意力编码装置、球、商品、药物和几何，策略先分配操作类型概率，再在该类型的合法候选中分配概率。这样不会仅因放置点数量多，就压低开始回合的概率。当前没有人工装置排名或固定连招。

实际采样的普通动作使用 PPO 更新；搜索改选的动作使用访问分布监督，避免把搜索动作错误当作原策略的在策略样本。价值训练使用不折扣剩余得分。技术截断时使用价值估计自举，并单独记录截断，不将其伪装为游戏结束。

## 5. 独立评估与观看

```powershell
.utmp\game-ai\venv\Scripts\python.exe Tools/GameAI/run.py evaluate --checkpoint .utmp/game-ai/runs/search/latest.pt --episodes 30 --search 16 --output .utmp/game-ai/runs/evaluation
.utmp\game-ai\venv\Scripts\python.exe Tools/GameAI/run.py evaluate --checkpoint .utmp/game-ai/runs/search/latest.pt --episodes 1 --visible --output .utmp/game-ai/runs/watch
```

评估默认使用 `--seed + 1000000` 开始的种子区间，训练使用 `--seed` 起始区间；真实种子逐局记录。正式选模型应再划分验证集和最终测试集，避免反复看同一测试集来调参。评估关闭搜索根节点的训练噪声。

默认评估从学到的策略分布采样，与 PPO 实际训练的策略一致；搜索阶段选择访问次数最多的动作。加 `--greedy` 可对照测试每次选择最大概率动作。短训练模型可能在这种确定性选择下持续等待；达到上限仍记作截断，不能当作正常终局得分。

`--visible` 显示真实 Player。AI 按协议逐段推进模拟，播放速度取决于推理/搜索时间，未做正常速度录像播放器。正式模型当前通过 Python 推理控制 Unity，不要求在 Unity 中安装机器学习推理包。

主要输出：

- `latest.pt`：网络、优化器和实验元数据，可继续训练。
- `manifest.json`：运行参数、游戏内容哈希、构建清单和版本信息。
- `episode-*.json`：种子、操作、逐步摘要、奖励与终局，供回放核对。
- `metrics.jsonl`：逐局得分、终局/截断状态、耗时和训练损失。
- `summary.json`：已完成对局的分数统计、Bootstrap 区间和截断数。

每次运行使用新的输出目录；非空目录会被拒绝，避免覆盖回放或混入旧指标。不传 `--output` 时自动生成时间戳目录。续训用 `--checkpoint` 读取旧模型，并写入新目录。

统计中的 `ticks_per_second` 包括当前命令的搜索/训练开销，是整体吞吐量，不是 PhysX 单独的性能。若很多局被截断，只看完成局均值会产生选择偏差，应同时检查完成率与截断率。

长期保留的模型可以从 `.utmp` 复制到 `Assets/AI/Models`，对应报告放 `docs/AI`。不要把唯一的正式训练成果长期只留在临时目录。

## 6. 自动测试

在项目根目录执行：

```powershell
$env:TEMP = Join-Path (Get-Location) '.utmp/game-ai/temp'
$env:TMP = $env:TEMP
$env:PYTHONDONTWRITEBYTECODE = '1'
$env:PYTHONPATH = Join-Path (Get-Location) 'Tools/GameAI'
.utmp\game-ai\venv\Scripts\python.exe -m unittest discover -s Tools/GameAI/tests -v
```

Unity 测试可用以下脚本运行：

```powershell
.\Tools\GameAI\test-unity.ps1 -UnityEditor '实际的 Unity.exe 完整路径'
```

脚本先运行 EditMode 的 `GameAI.Tests`，验证合法性查询不修改布局、拒绝碰撞和非有限坐标，并与真正放置结果保持一致；再运行 PlayMode 的 `MResLuaTests`，验证原有 Lua 生命周期、物理回调和新的显式时钟。报告和日志放在 `.utmp/game-ai`。

Python 测试包含奖励学习、操作类别概率、搜索平均随机收益、PPO/搜索训练分离、检查点往返、协议错误传播和回放拒绝。它们只验证算法与接口，不证明模型已经学会真实游戏。

## 7. 当前边界

- 已验证完整流程与选定的物理/Lua 行为，但只进行了短训练。尚未完成全部装置组合、正常交互帧循环和长时间训练的全面对照，不能据此下策略强度或数值平衡结论。
- 搜索支持无球 Shop/Build 边界，采用完整前缀重放。没有实现任意物理时刻的快照恢复，也没有实时阶段树搜索。
- 同一动作前缀在不同平台、Unity 版本或物理环境中可能不同；摘要检查会阻止继续搜索。通过可见摘要并不等于数学证明所有隐藏物理状态一致，仍需真实物理对照。
- 显式 MRes 时钟覆盖当前脚本生命周期。新增依赖其他 MonoBehaviour Update/FixedUpdate、全局随机源或帧时间的玩法时，需要加入驱动契约并重新验证。
- 当前观察使用公开状态和装置状态文字，不包含 RNG；没有实现通用的隐藏状态信念模型和循环记忆。具有未公开跨回合随机状态的新装置需要另行处理。
- 增加内容、改变场景或数值后应重新构建并评估。模型词表或内容哈希不一致时拒绝直接载入。
- 模型文件不是已经训练好的强 AI。实际强度、训练时间和所需算力必须用真实游戏实验确认。
